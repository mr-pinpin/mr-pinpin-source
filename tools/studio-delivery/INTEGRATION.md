BusinessRuntime captures new trusted Python modules, validates route(status,JSON) responses (finite JSON), and reloads without restarting Studio. ## New helper files and app-owned work

NEW tools/studio/business/draft_pdf_delivery.py: read-only `chunk(store,body)` verifies saved chapter/version hash against Store, finds an exact immutable export receipt in `Store.root/deliveries/catalog.json`, resolves only beneath that directory, verifies PDF magic/size/SHA and returns bounded chunks. It does not register files, render, mutate Store, call providers or infer approvals. App owns catalog creation and route wiring. NEW tools/studio/web/workspace-dev/draft-pdf-download.js: `pdfBlob(rpc,selection)` / `downloadPDF(rpc,selection)` use the existing supplied RPC, validate every chunk and whole artifact then create/revoke a PDF Blob URL. No direct fetch or filesystem input.

App must first render an actual saved draft through prepare.py/render.cjs to an unpublished Store-root delivery folder; verify renderer receipt; atomically register `{chapterId,version,sourceVersionSHA256,language,artifactSHA256,storagePath,bytes}` in catalog. It must obtain SHA from the saved immutable version, never overwrite current version/artwork or infer production approval. Rendering is not a request-time operation (avoid30s RPC timeout). Helper operation requests accept only chapterId, version, sourceVersionSHA256, language, artifactSHA256 and offset. No path/URL/route field. Catalog paths are private server-owned; filename is synthesized from bounded identity.

Transport limits:64KiB raw chunk,<=96KiB JSON response,<=64MiB PDF,256KiB catalog/1024 entries,256-entry signature cache. Base64 overhead is4/3 (~87,384 characters per full raw chunk). Client enforces same byte/identity bounds and detects premature/truncated/changed data before download. A one-shot fullchapter base64 JSON response is not recommended. Each request should be a fast read of already-rendered bytes; no generation retry or background production.

## Proposed narrow stable protocol (not installed)

Expose trusted server capability metadata and a stable namespaced JSON operation envelope, rather than adding each product route forever. Example operation `draft.pdf.chunk.v1`: POST `/api/business/draft.pdf.chunk.v1`, effect read-only, typed bounded fields above, result maximum96KiB, read-only-view permitted. Business routes implement operation dispatch; metadata comes from trusted same-origin server and is pinned to active business bundle/version, never accepted from child messages. The parent bridge admits only registered IDs under the new namespace and validates declared schemas/bounds; unknown operations/fields/external paths fail closed. Read-only effects may execute in review views; mutations retain active-frame and readOnly denial and existing8MiB maximum (prefer smaller per-operation caps). Nonce/source/origin checks remain untouched. Metadata discovery/response validation and parent installation hooks require reviewed new versioned stable bridge artifact/canary, not a running-kernel edit or a monolithic product rewrite.

Needed tiny caller handoff: trusted parent obtains/validates capability metadata, activates only metadata matching active business bundle, passes registry to bridge validation and enforces response byte ceiling before returning to child. Server metadata GET/operation POST can use existing business route framing; no file serving addition needed. These hooks are proposed, not authored in existing host/routes. Coordinator owns canary/cutover. Until then the new UI helper fails at unavailable capability rather than disguising its action.
